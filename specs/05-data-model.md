Tables: users, user_invites, password_resets, refresh_tokens, platform_admins, businesses, services, staff, staff_services, availability_rules, availability_exceptions, time_off, time_zone_changes, outbox, bookings, idempotency_keys, notifications, booking_history.
No-overlap is enforced at the database level by locking the staff member's row inside a transaction, not just in application code (see [ADR 0002](../docs/adr/0002-booking-concurrency-row-lock.md)).
bookings stores staff_id, service_id, customer_id (the user who holds the booking), start_utc, end_utc, blocked_start_utc, blocked_end_utc, status, and cancelled_at, plus cancelled_by, cancellation_reason, created_at and a version column for optimistic concurrency. blocked_start_utc and blocked_end_utc are the booking's interval including buffers, fixed when the booking is made or rescheduled (see [ADR 0004](../docs/adr/0004-snapshot-buffers-on-booking.md)). The version column guards concurrent updates to an existing booking (e.g. a cancel racing a reschedule); it does not prevent overlapping bookings, which is handled by the staff row lock in ADR 0002.
idempotency_keys remembers the Idempotency-Key of each booking created with one (user_id, idempotency_key, request_hash, booking_id, created_at; T29, decided 2026-11-25; see the IdempotencyKey parameter in [specs/04-api.openapi.yaml](04-api.openapi.yaml)). user_id is the caller who sent the key and (user_id, idempotency_key) is the primary key, so keys belong to the caller; idempotency_key is up to 64 ASCII characters compared case-sensitively (ascii_bin). request_hash is the lowercase hex SHA-256 of the request's normalised fields (serviceId, staffId, startUtc, customerEmail, overrideMinimumNotice), used to refuse the same key for a different request. A row is inserted in the same transaction as the booking, with created_at equal to the booking's; only created bookings get a row. A row counts for 24 hours after created_at (the exact moment it turns 24 hours old it has expired); an expired row is replaced when its key is used again, and expired rows are deleted by the cleanup in T31, which an index on created_at serves. booking_id and user_id reference bookings and users.
booking_history records each booking's creation, including who made it (the customer, or a staff member or owner booking on their behalf), each reschedule (see [ADR 0003](../docs/adr/0003-reschedule-keeps-booking-id.md)) and each minimum-notice override (R3), whether on a new booking or a reschedule. A creation row is written in the same transaction as the booking. Each row records the booking ID, what changed, who made the change and when, and whether the minimum notice period was overridden. Columns: id, booking_id, type (Created or Rescheduled), actor_user_id, actor_role (Owner, Staff or Customer: the role the actor acted in, stored because a user can hold several roles), at, staff_id, start_utc and end_utc (the slot after the change), previous_staff_id, previous_start_utc and previous_end_utc (set only for Rescheduled), and minimum_notice_overridden.
services holds each business's services (id, business_id, name, duration_minutes, buffer_before_minutes, buffer_after_minutes, description, price, created_at). duration_minutes is 1 to 1440 and each buffer 0 to 1440; name and description are stored trimmed, and a blank description as null (decided 2026-11-19). price is DECIMAL(10,2), 0 to 99999999.99, shown to customers only; there is no currency column, because payments are a non-goal and nothing calculates with the price. Changing a service's duration or buffers affects only new bookings and reschedules (ADR 0004).
staff_services links staff to the services they can perform (staff_id, service_id; composite primary key). Slot viewing for a service covers all staff linked to it. A staff_services link, and a booking's staff member and service, must belong to the same business; the API enforces this, not the database (decided 2026-11-16).
users holds one row per person who logs in (id, email, password_hash, name, time_zone, created_at). email is unique, ignoring case but not accents (collation utf8mb4_0900_as_ci), so Ann@example.com and ann@example.com are the same email. password_hash is null for an account created by an admin or owner until its invite is accepted; an account without a password cannot log in.
user_invites holds set-password invites (id, user_id, token_hash, expires_at, used_at, created_by, created_at). An invite is created when an admin creates an owner, or an owner adds staff, for an email with no account or with an account that has no password yet (decided 2026-11-18); only the user's newest invite works. The API inserts the row without a token; the worker generates the token when it sends the invite email, stores only its hash and sets expires_at to 7 days later, so the token never passes through the queue (see [specs/06-events.md](06-events.md)). An invite is single-use: accepting it sets the user's password_hash and used_at on every pending invite of the user (decided 2026-11-18). "Newest" is by created_at, ties broken by the greater id; once a newer row exists, older rows stop working even before the newer one has been sent. An invite works only while expires_at is in the future (the exact expiry moment is expired) and the user has no password. token_hash, here and in password_resets, is the lowercase hex SHA-256 of the token's UTF-8 bytes, as for refresh tokens (decided 2026-11-18). time_zone is the user's IANA time zone, used to show times in their zone alongside the business's (R2). There is no user type column: one person can hold several roles, e.g. an owner who also takes bookings, or a staff member who is a customer elsewhere. Roles come from the links below, and every "who" column (cancelled_by, changed_by, the booking_history author) references users.
password_resets holds password recovery links (id, user_id, token_hash, expires_at, used_at, created_at; decided 2026-11-17). It works like user_invites: the API inserts a row without a token when recovery is requested, and the worker generates the token when it sends the email, stores only its hash and sets expires_at to 1 hour later (see [specs/06-events.md](06-events.md)). Only the user's newest row works, by created_at with ties broken by the greater id, as for user_invites: once a newer row exists, older links stop working even before the newer one has been sent (decided 2026-11-19). A link works only while expires_at is in the future (the exact expiry moment is expired) and used_at is null; it is single-use. The API skips creating a row, and sends no email, if the user's newest row is less than 5 minutes old. Setting a password through a link sets users.password_hash and the row's used_at, sets used_at on the user's pending user_invites (so invite links stop working), and revokes every refresh token for the user (refresh_tokens.revoked_at). Changing the password while logged in leaves the user's recovery links working (decided 2026-11-19). token_hash is unique.
refresh_tokens holds refresh tokens for login sessions (id, user_id, family_id, token_hash, expires_at, created_at, used_at, revoked_at; see [ADR 0010](../docs/adr/0010-refresh-token-rotation.md), decided 2026-11-17). Only the SHA-256 hash of each token is stored; token_hash is unique and required. family_id groups the tokens issued from one login (register, login or accept-invite) and its refreshes; it is not a foreign key. A refresh sets used_at on the presented row and inserts a new row in the same family, expiring 30 days later. A token is valid only while used_at and revoked_at are both null and expires_at is in the future. Presenting a used token, and logging out, set revoked_at on every row in the family that does not have it yet.
- Owner: businesses.owner_user_id, required and unique, so each business has exactly one owner and each user owns at most one business. An admin creates the business and its owner together; the owner then changes its settings.
- Staff: a staff row (id, user_id, business_id, removed_at, created_at; user_id and business_id unique together). A user can be staff at more than one business (decided 2026-11-16), with one row per business; roles are always resolved for the business the request concerns. The staff row, not the user, is what bookings, availability, time off and staff_services reference, and what the ADR 0002 lock is taken on. An owner who takes bookings also has a staff row in their business. Removing a staff member sets the row's removed_at instead of deleting it, so past bookings and history keep their staff_id; a removed staff member is not staff for authorization (specs/07-nfr.md) and gets no slots. Adding them again clears removed_at on the same row; its staff_services links, availability rules and exceptions are kept, so they offer the same services and hours as before (decided 2026-11-19). Removal takes the ADR 0002 lock on that row.
- Customer: any user. A booking's customer_id references users; there is no customers table.
- Admin: a platform_admins row (user_id primary key, granted_by, granted_at). Admin is platform-wide, not tied to a business. Rows are added and removed by an operator script, never through the API, and removing a row revokes the role. granted_by references users: the script must name an existing admin as the granter, and only the first (bootstrap) admin has granted_by null. The script is a command in the API binary (`admin grant|revoke|list`); it names users by email, and they must already have an account; a bootstrap grant works only while there are no admins; revoking the last admin is refused; granting an existing admin changes nothing (decided 2026-11-18). There is no seeded default or system account (decided 2026-11-16).
businesses holds each business (id, name, owner_user_id, created_at) and its settings, each with a default:
- time_zone: IANA time zone string, required, no default (R2).
- min_notice_minutes: minimum notice period, default 120, 0 to 525600 (one year) (R3).
- cancellation_window_hours: the cancellation window N, default 24, 0 to 8760 (one year) (R4).
- max_advance_days: maximum advance-booking window, default 21, 1 to 3650 (R8). Not capped for performance ([ADR 0005](../docs/adr/0005-limit-slot-query-range.md)); the 10-year ceiling only keeps date arithmetic in range.
- slot_step_minutes: slot step, default 30, 1 to 1440 (one day) (R8).
The maxima were decided 2026-11-19 and are enforced by the API (400) and by database check constraints.
Settings are read when a slot is generated or a booking is made or rescheduled; changing them never rewrites existing bookings.
bookings.status is either Confirmed or Cancelled. A booking is created Confirmed; cancelling it sets it to Cancelled and sets cancelled_at, cancelled_by and cancellation_reason. cancelled_by is the user who cancelled (the customer, staff member or owner; for R6, whoever confirmed the time off). cancellation_reason is one of CustomerCancelled, BusinessCancelled (a staff member or owner cancelled the booking directly), TimeOff (confirmed time off overlapped the booking, R6), AvailabilityChanged (a confirmed date exception, weekly availability change or business time zone change left the booking outside availability, R2, R6 and R8), or StaffRemoved (the owner confirmed removing the booking's staff member, R6). All three columns are null while the booking is Confirmed and required once it is Cancelled. Cancelled is final. Only Confirmed bookings are active: they alone count for overlap (R1, R7) and block slot generation (R8). A reschedule keeps the booking Confirmed.

availability_rules holds each staff member's weekly availability blocks (id, staff_id, day_of_week, start_local, end_local), in the business's local time (R2, R8); day_of_week is Monday to Sunday, and end_local is after start_local.
time_off holds a staff member's time off (id, staff_id, start_utc, end_utc, created_at); end_utc is after start_utc. Entries may overlap each other and may lie in the past (decided 2026-11-19); slot generation treats their union as blocked.
availability_exceptions holds date exceptions to a staff member's weekly availability (staff_id, date, start_local, end_local). Dates and times are local to the business's time zone (R2). A date with one or more rows replaces that staff member's weekly availability_rules for that date: each row with start_local and end_local is an available time range, and a single row with both null marks the whole day unavailable. A date cannot have both a null row and time ranges, and its time ranges cannot overlap. Dates without rows use the weekly availability_rules.
time_zone_changes records each change to a business's time zone (business_id, old_time_zone, new_time_zone, changed_by, changed_at). It is append-only (R2).
outbox holds events waiting to be published (id, seq, event_type, schema_version, message_group_id, payload JSON, created_at, published_at). The API inserts a row in the same transaction as the change that causes the event, and a relay publishes unpublished rows to SQS after commit (see [specs/06-events.md](06-events.md)). The row's id is the event's eventId. seq is an auto-increment number assigned by the database on insert; the relay publishes each message group's rows in seq order (decided 2026-11-23). Every write that adds an event for a message group holds a lock on that group's own row until it commits: the booking row (inserted, updated, or read FOR SHARE as the R4 rebook check does for RebookedInsideWindow), or the user's row. So within a group seq follows commit order. It is not used for ordering across groups, and gaps are fine. seq, attempts, last_error and next_attempt_at are the relay's columns: a failed publish increments attempts, records last_error (truncated to 1000 characters) and sets next_attempt_at for the retry. Published rows are kept for 30 days after published_at, to help trace a missing email, then deleted by the cleanup in T31; unpublished rows are never deleted (decided 2026-11-26).
notifications records each email the worker sends (id, event_id, recipient_user_id, kind, status, ses_message_id, error, created_at, sent_at). kind is one of Invite, AccessGranted, PasswordReset, PasswordChanged, Confirmation, Rescheduled, Cancelled, LocalTimeChanged, RebookedInsideWindow, Reminder24h or Reminder1h. status is Pending, Sent or Failed. (event_id, recipient_user_id) is unique, so each event emails each recipient at most once, even if the same user is notified in two roles (e.g. an owner who is also the staff member). Before sending, the worker inserts a Pending row, or finds the existing one: if it is Sent, the email is skipped as a duplicate; if it is Pending or Failed, the email is sent again. After sending, the row becomes Sent with ses_message_id and sent_at, or Failed with error. Email addresses are not stored; they are looked up from users when sending.
