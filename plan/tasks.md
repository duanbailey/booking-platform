# Task plan

Work one task at a time, in order, unless a task says otherwise. For each task (see `CLAUDE.md`):

1. Write tests from the listed acceptance criteria first (stories in `specs/02-requirements.md`, rules in `specs/03-business-rules.md`, endpoints in `specs/04-api.openapi.yaml`).
2. Implement until they pass.
3. Reference rule IDs in test names and code comments (e.g. `// R7`).
4. If code and spec disagree, stop and ask.

Mark a task `[x]` when its "Done when" holds. A task that touches the schema adds a migration; the schema is never edited by hand.

- Outbox ordering (2026-11-23, was under Decisions needed): an auto-increment `seq` column on `outbox`, assigned by the database on insert; the relay publishes each message group's rows in `seq` order, never by `created_at` (each API instance's clock) or `id` (random within a millisecond). Every write that adds an event for a group holds a lock on the group's own row until commit (the booking row: inserted, updated, or read FOR SHARE by the R4 rebook check; or the user's row), so within a group `seq` follows commit order; it is not used across groups and gaps are fine. Alternatives considered: the database clock for `created_at` (ties within a transaction), ordering by `bookingVersion` (doesn't cover user-group events or RebookedInsideWindow), monotonic v7 GUIDs (don't fix clock skew between instances), an order-tolerant worker (a possible later safety net), binlog CDC (against ADR 0008). Recorded in `specs/05-data-model.md` and `specs/06-events.md`.

- T25 reminders (2026-11-24, all confirmed): EventBridge Scheduler delivers ReminderDue through the SQS FIFO queue (target = the queue, message group = the booking ID), so it takes the same handler path, retries and dead-letter queue as every event; T27 turns on content-based deduplication on the queue (Scheduler cannot set a deduplication ID; the relay's explicit IDs take precedence). Reminders are due exactly 24 hours and 1 hour of elapsed time before the start (UTC). Schedules are one-time `at(...)` expressions in UTC named `reminder-<bookingId>-24h` / `-1h`, in a schedule group from config, with no flexible window, deleted by Scheduler after running (ActionAfterCompletion DELETE); creating is create-or-update on conflict, deleting ignores not-found. ReminderDue: reads bookings (id, staff_id, service_id, customer_id, start_utc, end_utc, status), services (business_id) and businesses (time_zone, the current zone) besides T24's reads; a missing booking fails the message; the reminder is dropped (logged) if the booking is not Confirmed, starts at a different time than `scheduledForStartUtc`, or has already started. Config: REMINDER_GROUP, REMINDER_TARGET_ARN (the queue), REMINDER_ROLE_ARN (the role Scheduler uses to send); retry policy and Scheduler's own dead-letter setup are T27's.

- T21 outbox relay (2026-11-23): the real-AWS test (ADR 0007) is written in T21, tagged, and skips unless a test queue URL is configured, so ordinary runs stay offline; it runs once T27 provisions a dev queue (or one is made by hand). Published rows are kept (no cleanup in T21; see T31). Defaults (confirmed 2026-11-23): each round claims up to 10 rows, at most one per message group (its earliest unpublished row, unless that row is waiting for a retry), FOR UPDATE SKIP LOCKED in seq order, holding the locks while sending and setting published_at in the same transaction; a round that published anything is followed at once by another, otherwise the relay waits 1 s (configurable); the SQS body is the stored envelope as MySQL returns the JSON column (same content as written, but canonical: keys sorted and MySQL's spacing, so consumers must not depend on key order or bytes; corrected after review), MessageGroupId = message_group_id, MessageDeduplicationId = eventId, no message attributes; a failed row backs off from 1 s doubling to at most 60 s (columns attempts, last_error, next_attempt_at), logged with event ID, group and attempt count, never the payload; AWSSDK.SQS (Apache-2.0) with the default credential chain, configured by Outbox:QueueUrl, timing out after 10 s per attempt with at most 2 retries (added after review, so a hung call is an ordinary failure); seq is BIGINT AUTO_INCREMENT and unique, existing rows numbered in table order, and the dev backlog is published as-is; on shutdown the relay stops claiming and finishes the round in flight; docs/architecture.md marks the relay as built.
- T20 removing staff (2026-11-23): removing a member who is already removed is a 200 no-op (the row with its original `removedAt`; nothing changes, no events); the owner may remove their own staff row (same R6 rules; they stay the owner and may add themselves back); a removed member's pending invite is left alone (accepting it only sets a password on what is now a plain account; access is checked per request). - T19 availability changes with R6 (2026-11-23): a booking is outside availability when its appointment [start, end) no longer lies inside a single block of its date (buffers excluded, R8; touching blocks stay separate, ADR 0011); step alignment does not count, so a booking that still fits stays even if its start is no longer an offered step. A booking's date is the business-local date of its start. Block edges resolve as in slot generation (R2): a start in a spring-forward gap to the gap's end, an ambiguous start to its earlier occurrence, an end in a gap to the gap's end, an ambiguous end to its later occurrence. Affected bookings are Confirmed bookings that have not started (start after now, as the API spec says; unlike time off, a booking in progress is never affected) on the dates the change governs: a weekly PUT checks dates without a date exception, an exception PUT or DELETE checks that date only; every such booking outside the new availability is listed, even one already outside before. A malformed, empty or repeated `confirmAffectedBookingIds` (or a repeated ID) is 400 naming it; spaces around an ID are ignored (code review). Defaults: the confirm pattern and cancellation as in T18 (reason `AvailabilityChanged`, actor role Owner if the caller owns the business, else Staff, one transaction; the R4 window doesn't apply); the 404 for a missing exception comes before the R6 check. Locks: the confirming user's row FOR SHARE, then the staff row.
- T18 time off with R6 (2026-11-20): the affected bookings are the staff member's Confirmed bookings that have not ended (end after now) and whose blocked interval overlaps the time off (half-open), so past time off never cancels bookings that already happened; an appointment in progress counts. A booking whose appointment has ended but whose after-buffer is still running does not count (code review: confirming would cancel, and notify the customer about, an appointment that already happened). Defaults: the confirm pattern as in T15 (exact set, empty set goes ahead, `rule` R6, ordered by start then id); on confirmation the time off is saved and each affected booking is cancelled in the same transaction with reason `TimeOff`, `cancelled_by` the confirming user, `version` + 1 and one `BookingCancelled` per booking whose actor role is Owner if the caller owns the business, else Staff; the R4 window doesn't apply. Locks: the confirming user's row FOR SHARE, then the staff row (StaffAccessGuard). Every writer of a booking holds its staff member's lock, so the bookings can't change after they are read. After code review: the affected bookings are cancelled with one UPDATE (fewer round trips under the staff lock), and the 409 message says confirming notifies everyone affected (customers and the staff member).
- T17 cancel and reschedule (2026-11-20): a caller who is both the booking's customer and its staff member or the owner is never blocked by the R4 window; inside the window they used a staff privilege (cancel reason `BusinessCancelled`, actor role Owner or Staff), outside it they act as the customer (`CustomerCancelled`, role Customer), the same 'privilege used' rule as T14's history role. A reschedule to the booking's current staff member and start is a 200 no-op (no history, no event, version and buffers unchanged), after the access, cancelled and window checks. Staff and owners may cancel or reschedule a booking that has already started or ended (no error code exists; the new slot must still be offered). Check order: 404 (can't view the booking; a staffId outside the business), 403 (customer changing staff, staff moving to another staff member, override not allowed), 422 `BookingCancelled`, 422 `CancellationWindowPassed` (customer only), then T14's order for the new slot, with the booking's own current slot ignored for overlap (ADR 0003). Defaults: the window is inclusive (start - now >= N hours may be cancelled or moved by the customer), checked on the current start; locks before any staff lock, in id order (ADR 0002 'Implicit locks on user rows count'): cancel takes the actor's and the customer's rows FOR SHARE (so a reschedule can't move the booking to another staff member meanwhile), reschedule the actor's FOR SHARE and the customer's FOR UPDATE; then the booking's staff row and, for a move between staff, both staff rows in id order; each change increments `version`, which is also checked on save; the override is recorded only when it was needed; reschedule has no R4 rebook check (R4's rebook paragraph is about making a booking). After code review: cancel and reschedule run at READ COMMITTED; the booking's staff member is read after the user rows are held (a move needs the customer's row FOR UPDATE, so it can't change after that), its staff row(s) are locked, then the booking is read FOR UPDATE, so there is no retry loop and a second simultaneous cancel gets 422 `BookingCancelled`. (At REPEATABLE READ, that read before the staff lock would fix the snapshot too early.)
- T16 reading bookings (2026-11-20): on `GET /v1/businesses/{businessId}/bookings`, anyone but the owner and the business's active staff gets 404 (as availability and time off), and so does an unknown business; the owner's `staffId` must be a staff row of the business (else 404; a removed member is allowed, for their past bookings); staff see only their own staff row's bookings and another `staffId` is 403; an owner who is also staff sees everything. - T15 confirm pattern and R4 rebook (2026-11-20): a booking is inside the window when it is Confirmed, with the same business (any staff or service), and has not started: now < start < now + N hours (exactly N hours away is outside, as cancelling then is allowed; N = 0 never triggers). The confirm pattern matches on the exact set: the change goes ahead only if `confirm.affectedBookingIds` equals the affected set recomputed under the lock, else 409 `ConfirmationRequired` with the current list; when the recomputed set is empty the change goes ahead whether or not `confirm` was sent. `affectedBookings` is ordered by start, then id. `ConfirmationRequired` is checked last, after `SlotConflict`. - T14 bookings (2026-11-20): the 409 `SlotConflict` details are the requested slot (staff, start, end), never the other booking's times.
