# Task plan

Work one task at a time, in order, unless a task says otherwise. For each task (see `CLAUDE.md`):

1. Write tests from the listed acceptance criteria first (stories in `specs/02-requirements.md`, rules in `specs/03-business-rules.md`, endpoints in `specs/04-api.openapi.yaml`).
2. Implement until they pass.
3. Reference rule IDs in test names and code comments (e.g. `// R7`).
4. If code and spec disagree, stop and ask.

Mark a task `[x]` when its "Done when" holds. A task that touches the schema adds a migration; the schema is never edited by hand.

- Auth details (T4): `PasswordHasher` (PBKDF2) for passwords; login gives one `InvalidCredentials` for every failure with similar timing; 10 requests per minute per IP on `/v1/auth/`, 60 for refresh and logout (429 `RequestRejected`); email and name trimmed, checked after trimming; IANA time zone names only, aliases accepted and stored under their canonical name (amended 2026-11-20 after the T13 code review: e.g. UTC is stored as Etc/UTC); null in `PATCH /v1/me` gives 400; a sign-up race is decided by the unique index, 2026-11-17.
- Password recovery and change (stories added 2026-11-17): same 202 whether or not an account exists; `password_resets` table like invites (worker makes the token, 1-hour link, single use, newest only); one recovery email per account per 5 minutes; a link also works for an account with no password yet (accepts the invite); reset and change revoke every refresh token; change returns new tokens, wrong current password is 422 `CurrentPasswordIncorrect`, endpoint under `/v1/auth/` for the rate limit; `PasswordChanged` email after both, 2026-11-17.
- Outbox ordering (2026-11-23, was under Decisions needed): an auto-increment `seq` column on `outbox`, assigned by the database on insert; the relay publishes each message group's rows in `seq` order, never by `created_at` (each API instance's clock) or `id` (random within a millisecond). Every write that adds an event for a group holds a lock on the group's own row until commit (the booking row: inserted, updated, or read FOR SHARE by the R4 rebook check; or the user's row), so within a group `seq` follows commit order; it is not used across groups and gaps are fine. Alternatives considered: the database clock for `created_at` (ties within a transaction), ordering by `bookingVersion` (doesn't cover user-group events or RebookedInsideWindow), monotonic v7 GUIDs (don't fix clock skew between instances), an order-tolerant worker (a possible later safety net), binlog CDC (against ADR 0008). Recorded in `specs/05-data-model.md` and `specs/06-events.md`.
- T23 worker skeleton (2026-11-23): the Jest tests run against a throwaway MySQL database whose schema global setup generates with `dotnet ef migrations script` (so it always matches the migrations; local MySQL on 3307 or `BOOKING_TEST_MYSQL`, as the C# tests); T23 ships no production handler: tests register a test-only handler to prove that a duplicate event sends each recipient at most one email, and every event type without a handler yet fails into the dead-letter queue like an unknown one until T24-T26; in a Lambda batch the first failed message and every later one are reported failed (ReportBatchItemFailures), as AWS documents for FIFO queues. Defaults (confirmed): ajv (draft 2020-12) with ajv-formats validating against `specs/events` copied into the build, mysql2 and @aws-sdk/client-sesv2 at exact versions; invalid JSON, a failed envelope or schema check, or an unknown `eventType` or `schemaVersion` throws (retried, then the dead-letter queue), logged with eventId, eventType and correlationId when readable, never the body; per recipient a Pending `notifications` row is inserted or found (Sent: skip; Pending or Failed: send), contact details (email, name, time zone, never `password_hash`) are read just before sending, a send error marks the row Failed with the error and retries the message, and a crash between sending and marking Sent can send twice, as the spec accepts; an `EmailSender` interface (to, subject, text, HTML; returns the SES message ID) with an in-memory fake and a tagged real-SES test skipped unless configured, From address from config; JSON log lines on stdout with level, message, correlationId, eventId and eventType; Node 22 or later; database settings from environment variables until T27. After review: error text in logs has email addresses replaced by `[email]` (provider errors can name the recipient; the notifications row keeps the full text); a row is marked Failed only when the contact lookup, composing or sending fails, so a failure to record Sent leaves it Pending (the retry sends again, as the spec accepts); `specs/events/examples` holds every event the API publishes exactly as the relay sends it (C# `EventExamplesTests` writes them through the real OutboxWriter and MySQL and fails on drift; regenerate with `UPDATE_EVENT_EXAMPLES=1`), and the worker's tests validate every example, so the two validators can't silently disagree.
- T24 booking emails (2026-11-24, all confirmed): plain-text emails, no links (no app URL until T26), English. Times (R2) show the business's zone first and the recipient's own zone (`users.time_zone`) only when it differs, as a 24-hour range with the date, the IANA name and the UTC offset (e.g. `Monday 23 November 2026, 14:00-15:00 America/New_York (UTC-05:00)`; the offset tells the two fall-back hours apart; a range ending on another local date names both dates), plus the duration as elapsed time. The business's zone is the one in the event (BookingLocalTimeChanged: old local time in the old zone, new in the new zone); names (business, service, staff, customer) are read when sending, so they are current then. Lookups: `businesses` (id, name, owner_user_id), `services` (id, name), `staff` (id, user_id) and `bookings` (id, service_id, for the RebookedInsideWindow email's services); a missing row fails the message (dead-letter queue). Events are sent as they are, never checked for staleness (only ReminderDue is, T25). Staff- and owner-facing emails name the customer and give their email. Cancellations: one email per booking per recipient (no StaffRemoved summary), with one sentence by reason and recipient and no actor names: CustomerCancelled, BusinessCancelled, TimeOff and AvailabilityChanged (the staff member is no longer available then), StaffRemoved (to the removed member: they were removed as staff at the business, so the booking was cancelled; to the customer: their staff member is no longer available at the business). Reschedule to another staff member: the customer sees old and new time and staff, the old staff member that the booking moved to the new one, the new staff member that a booking moved to them, all kind Rescheduled. A user in two roles gets one email per event (the notifications key): the customer is emailed first, so the customer wording wins; for RebookedInsideWindow the staff member before the owner.
- T25 reminders (2026-11-24, all confirmed): EventBridge Scheduler delivers ReminderDue through the SQS FIFO queue (target = the queue, message group = the booking ID), so it takes the same handler path, retries and dead-letter queue as every event; T27 turns on content-based deduplication on the queue (Scheduler cannot set a deduplication ID; the relay's explicit IDs take precedence). Reminders are due exactly 24 hours and 1 hour of elapsed time before the start (UTC). Schedules are one-time `at(...)` expressions in UTC named `reminder-<bookingId>-24h` / `-1h`, in a schedule group from config, with no flexible window, deleted by Scheduler after running (ActionAfterCompletion DELETE); creating is create-or-update on conflict, deleting ignores not-found. The ReminderDue eventId is a UUIDv5 of the causing event's eventId and the reminder type, so each create or move gets a new ID while a redelivered event writes the same one; occurredAt is the due time and correlationId the causing event's. BookingCreated skips reminders already due; BookingRescheduled moves them and deletes any already due at the new start; BookingCancelled deletes both; emails go first, then the reminder changes. ReminderDue: reads bookings (id, staff_id, service_id, customer_id, start_utc, end_utc, status), services (business_id) and businesses (time_zone, the current zone) besides T24's reads; a missing booking fails the message; the reminder is dropped (logged) if the booking is not Confirmed, starts at a different time than `scheduledForStartUtc`, or has already started. The email is in the T24 style (kind Reminder24h or Reminder1h). Config: REMINDER_GROUP, REMINDER_TARGET_ARN (the queue), REMINDER_ROLE_ARN (the role Scheduler uses to send); retry policy and Scheduler's own dead-letter setup are T27's.
- T22 business time zone change (2026-11-23): a remaining booking gets `BookingLocalTimeChanged` when its local start or its local end (date and time) differs between the old and new zone, so a booking whose end moves only because the zones' DST rules differ is notified too; the `TimeZoneChange` schema gains a required `id` (the row `timeZoneChangeId` points at); the 409 carries `rule` R6, like every other confirmation that cancels bookings. Defaults: locks are the owner's row FOR SHARE, the business row FOR UPDATE, every staff row of the business (removed ones included) in id order, then each booking that gets `BookingLocalTimeChanged` FOR UPDATE by primary key (ADR 0002 amendment); affected bookings are Confirmed ones that have not started, of any staff member, checked against each date's availability in the new zone (exceptions if any, else weekly; containment only, as T19), and a booking in progress is neither cancelled nor notified; check order 400, 404 (unknown business), 403 (not the owner), then the zone is canonicalized and the current zone (an alias too) is a 200 no-op decided under the locks, then the confirm pattern; on confirmation one transaction stores the canonical zone, writes the `time_zone_changes` row (old, new, owner, now), cancels the outside bookings (`AvailabilityChanged`, role Owner) and writes one `BookingLocalTimeChanged` per remaining changed booking; the `BookingCancelled` events of bookings this change cancels carry the old zone as `businessTimeZone`, the zone the customer booked in (decided 2026-11-23); the list is owner only (404 unknown business, 403 others), newest first by `changedAt` then id, with its own cursor kind. After review: a fixed number of statements under the locks (bookings, weekly rules and exceptions read once each, the moved bookings locked in one statement), since every booking of the business waits on them; the stored zone is canonicalized before the no-op check (a business saved before T13 may hold an alias such as UTC).
- T21 outbox relay (2026-11-23): the real-AWS test (ADR 0007) is written in T21, tagged, and skips unless a test queue URL is configured, so ordinary runs stay offline; it runs once T27 provisions a dev queue (or one is made by hand). With no queue URL configured the relay doesn't run in Development and tests (rows stay unpublished, one startup log line), and startup fails in any other environment, so a deployment can't silently stop sending email. A row that keeps failing is retried forever with backoff, holding back only its own message group; failures are tracked on the row (attempts, last error) and logged as errors for an alarm (T27); nothing is skipped silently. Published rows are kept (no cleanup in T21; see T31). Defaults (confirmed 2026-11-23): each round claims up to 10 rows, at most one per message group (its earliest unpublished row, unless that row is waiting for a retry), FOR UPDATE SKIP LOCKED in seq order, holding the locks while sending and setting published_at in the same transaction; a round that published anything is followed at once by another, otherwise the relay waits 1 s (configurable); the SQS body is the stored envelope as MySQL returns the JSON column (same content as written, but canonical: keys sorted and MySQL's spacing, so consumers must not depend on key order or bytes; corrected after review), MessageGroupId = message_group_id, MessageDeduplicationId = eventId, no message attributes; a failed row backs off from 1 s doubling to at most 60 s (columns attempts, last_error, next_attempt_at), logged with event ID, group and attempt count, never the payload; AWSSDK.SQS (Apache-2.0) with the default credential chain, configured by Outbox:QueueUrl, timing out after 10 s per attempt with at most 2 retries (added after review, so a hung call is an ordinary failure); seq is BIGINT AUTO_INCREMENT and unique, existing rows numbered in table order, and the dev backlog is published as-is; on shutdown the relay stops claiming and finishes the round in flight; docs/architecture.md marks the relay as built.
- T20 removing staff (2026-11-23): removing a member who is already removed is a 200 no-op (the row with its original `removedAt`; nothing changes, no events); the owner may remove their own staff row (same R6 rules; they stay the owner and may add themselves back); a removed member's pending invite is left alone (accepting it only sets a password on what is now a plain account; access is checked per request). Defaults: the body is optional (none, empty or `{}` means not confirmed; `confirm` validated as elsewhere); affected = the member's Confirmed bookings that have not started (start after now, R6), so a booking in progress stays Confirmed and the owner can still cancel it; the confirm pattern as in T18 (exact set, `rule` R6, ordered by start then id), cancelled with reason `StaffRemoved`, actor role Owner, in the same transaction that sets `removed_at`; no event for the removal itself (only `BookingCancelled` per booking); availability, time off and service links are kept, so restoring brings them back (T10); `removedAt` is truncated to the microsecond before it is stored, so the response matches the stored value (found with curl). Access as T10's owner-only staff writes: 404 only if the staff member doesn't exist, 403 for anyone but the business's owner. Locks: the owner's row FOR SHARE, then the staff row; the affected set and `removed_at` are read under them.
- T19 availability changes with R6 (2026-11-23): a booking is outside availability when its appointment [start, end) no longer lies inside a single block of its date (buffers excluded, R8; touching blocks stay separate, ADR 0011); step alignment does not count, so a booking that still fits stays even if its start is no longer an offered step. A booking's date is the business-local date of its start. Block edges resolve as in slot generation (R2): a start in a spring-forward gap to the gap's end, an ambiguous start to its earlier occurrence, an end in a gap to the gap's end, an ambiguous end to its later occurrence. Affected bookings are Confirmed bookings that have not started (start after now, as the API spec says; unlike time off, a booking in progress is never affected) on the dates the change governs: a weekly PUT checks dates without a date exception, an exception PUT or DELETE checks that date only; every such booking outside the new availability is listed, even one already outside before. A malformed, empty or repeated `confirmAffectedBookingIds` (or a repeated ID) is 400 naming it; spaces around an ID are ignored (code review). Defaults: the confirm pattern and cancellation as in T18 (reason `AvailabilityChanged`, actor role Owner if the caller owns the business, else Staff, one transaction; the R4 window doesn't apply); the 404 for a missing exception comes before the R6 check. Locks: the confirming user's row FOR SHARE, then the staff row.
- T18 time off with R6 (2026-11-20): the affected bookings are the staff member's Confirmed bookings that have not ended (end after now) and whose blocked interval overlaps the time off (half-open), so past time off never cancels bookings that already happened; an appointment in progress counts. A booking whose appointment has ended but whose after-buffer is still running does not count (code review: confirming would cancel, and notify the customer about, an appointment that already happened). Defaults: the confirm pattern as in T15 (exact set, empty set goes ahead, `rule` R6, ordered by start then id); on confirmation the time off is saved and each affected booking is cancelled in the same transaction with reason `TimeOff`, `cancelled_by` the confirming user, `version` + 1 and one `BookingCancelled` per booking whose actor role is Owner if the caller owns the business, else Staff; the R4 window doesn't apply. Locks: the confirming user's row FOR SHARE, then the staff row (StaffAccessGuard). Every writer of a booking holds its staff member's lock, so the bookings can't change after they are read. After code review: the affected bookings are cancelled with one UPDATE (fewer round trips under the staff lock), and the 409 message says confirming notifies everyone affected (customers and the staff member).
- T17 cancel and reschedule (2026-11-20): a caller who is both the booking's customer and its staff member or the owner is never blocked by the R4 window; inside the window they used a staff privilege (cancel reason `BusinessCancelled`, actor role Owner or Staff), outside it they act as the customer (`CustomerCancelled`, role Customer), the same 'privilege used' rule as T14's history role. A reschedule to the booking's current staff member and start is a 200 no-op (no history, no event, version and buffers unchanged), after the access, cancelled and window checks. Staff and owners may cancel or reschedule a booking that has already started or ended (no error code exists; the new slot must still be offered). Check order: 404 (can't view the booking; a staffId outside the business), 403 (customer changing staff, staff moving to another staff member, override not allowed), 422 `BookingCancelled`, 422 `CancellationWindowPassed` (customer only), then T14's order for the new slot, with the booking's own current slot ignored for overlap (ADR 0003). Defaults: the window is inclusive (start - now >= N hours may be cancelled or moved by the customer), checked on the current start; locks before any staff lock, in id order (ADR 0002 'Implicit locks on user rows count'): cancel takes the actor's and the customer's rows FOR SHARE (so a reschedule can't move the booking to another staff member meanwhile), reschedule the actor's FOR SHARE and the customer's FOR UPDATE; then the booking's staff row and, for a move between staff, both staff rows in id order; each change increments `version`, which is also checked on save; the override is recorded only when it was needed; reschedule has no R4 rebook check (R4's rebook paragraph is about making a booking). After code review: cancel and reschedule run at READ COMMITTED; the booking's staff member is read after the user rows are held (a move needs the customer's row FOR UPDATE, so it can't change after that), its staff row(s) are locked, then the booking is read FOR UPDATE, so there is no retry loop and a second simultaneous cancel gets 422 `BookingCancelled`. (At REPEATABLE READ, that read before the staff lock would fix the snapshot too early.)
- T16 reading bookings (2026-11-20): on `GET /v1/businesses/{businessId}/bookings`, anyone but the owner and the business's active staff gets 404 (as availability and time off), and so does an unknown business; the owner's `staffId` must be a staff row of the business (else 404; a removed member is allowed, for their past bookings); staff see only their own staff row's bookings and another `staffId` is 403; an owner who is also staff sees everything. Defaults (existing conventions): lists ordered by start, then id, with the start/id cursor; `from` inclusive and `to` exclusive on the start; `from` after `to` is 400 naming `from`; no `status` lists both; history ordered by `at`, then id; `actor.name` is the user's current name (history stores no name); `actor.userId` (shown to the booking's staff member and the owner) and `previousSlot` (Rescheduled only) are omitted, not null, when they don't apply; a removed staff member gets 404 for their old bookings and their history (AccessResolver, T3). After code review: start/id cursors carry the kind of list (booking lists, booking history, time off), so a cursor from another kind is 400 naming `cursor` (both booking lists are one kind); a `(staff_id, start_utc)` index (migration BookingsStaffStartIndex) serves the staff and business lists, with each list's scope inside the keyset query.
- T15 confirm pattern and R4 rebook (2026-11-20): a booking is inside the window when it is Confirmed, with the same business (any staff or service), and has not started: now < start < now + N hours (exactly N hours away is outside, as cancelling then is allowed; N = 0 never triggers). The confirm pattern matches on the exact set: the change goes ahead only if `confirm.affectedBookingIds` equals the affected set recomputed under the lock, else 409 `ConfirmationRequired` with the current list; when the recomputed set is empty the change goes ahead whether or not `confirm` was sent. `affectedBookings` is ordered by start, then id. `ConfirmationRequired` is checked last, after `SlotConflict`. Booking creation locks the customer's user row FOR UPDATE (the caller's stays FOR SHARE), so one customer's bookings run one at a time across staff and the R4 check sees them all. Staff booking on behalf see every affected booking, a colleague's included (an exception to the view rule, specs/07-nfr.md). One `RebookedInsideWindow` per original booking. Defaults: the 409 message tells a customer booking for themselves to contact the business to cancel the original, and tells staff and owners that the original still stands.
- T14 bookings (2026-11-20): the 409 `SlotConflict` details are the requested slot (staff, start, end), never the other booking's times. Check order: 400, 404 (service, or a staffId outside the service's business), 403 (customerEmail or override not allowed), 422 `CustomerNotFound`, 422 `SlotUnavailable` for a removed staff member, 422 `StaffNotAssignedToService` for an active unassigned one, 422 `SlotUnavailable` when the start is in the past or not offered even ignoring the notice period and bookings (availability, step, advance window, time off), 422 `MinimumNotice` (only for a start that would otherwise be offered), then 409 `SlotConflict` (a Confirmed booking's blocked interval overlaps, R1). History actor role: Customer for a plain self-booking; Owner or Staff when booking on behalf or using the override (Owner when the caller is both); `minimumNoticeOverridden` is true only when the start really was inside the notice period (the permission check applies whenever the flag is set). An account without a password counts as an account for `customerEmail`. Before the staff lock, the customer's and actor's user rows are locked in id order (the booking and history inserts' foreign keys would otherwise take those locks after the staff lock, against ADR 0002's order); T14 took both FOR SHARE, superseded by T15 (2026-11-20): the customer's row is FOR UPDATE, the actor's stays FOR SHARE. `confirm` was validated and ignored in T14; T15 enforces it.
- T13 slots (2026-11-20): NodaTime with its embedded tzdb resolves local times, so DST rules are the same on every OS (zone-name validation moves to it too). `staffId` not a staff row of the service's business is 404; a removed or unassigned member gives 200 with no slots. A slot is offered when start ≥ now + minimum notice (inclusive; start ≥ now with `ignoreMinimumNotice`) and start ≤ now + maxAdvanceDays × 24 h; T14 reuses the check. Steps are counted on the local wall clock from each block start; local times in a spring-forward gap are dropped, repeated fall-back times are offered at their first occurrence only; a block edge inside a gap resolves to the instant the gap ends, an ambiguous block start to its earlier and an ambiguous end to its later occurrence; every slot lasts exactly the service duration in elapsed time. Overlap checks (R1) are per staff row, so a user who is staff at two businesses has independent schedules. Slots ordered by start, then staffId. Touching availability blocks are not merged: each bounds slots on its own, so no slot crosses from one into the next (R8, decided after code review). After code review: a stored zone that tzdb lacks falls back to the OS zone data (names were validated against it before T13) with a warning logged; a zone neither knows is a 500.
- T12 time off (2026-11-19): viewed like availability (owner and the business's active staff; owner also for a removed member); time off may overlap other time off and may be in the past; UtcTimestamp strictly with Z (shared check, reused by T14); the time-off list filters on overlap (ends after `from`, starts before `to`), unlike the start-based FromUtc/ToUtc of other lists. Defaults: list by start then id; writes check access, lock the staff row, re-check; timestamps kept to the microsecond; the existing (staff_id, start_utc) index serves the list (InnoDB appends id).
- T11 availability (2026-11-19): viewing raw availability is for the owner and the business's active staff (404 for others; customers see slots); the owner may view and set a removed member's availability, the member gets 404; LocalTime stays HH:mm, so availability ends at 23:59 at the latest; DELETE of a date with no exception is 404. Defaults: past dates may have exceptions; `confirm` (and `confirmAffectedBookingIds`) accepted and ignored until T19; writes lock the staff row; a malformed path date is 400 naming `date`.
- T10 staff (2026-11-19): no AccessGranted when the owner adds themselves; restoring keeps service links and availability; PUT services allowed for a removed staff member; a new staff account gets the business's time zone. Defaults: staff list by name then staffId; PUT response by service name then id; adding locks the user row then the staff row (as T6/T7); PUT locks the staff row so replacements never interleave.
- Pagination and T9 services (2026-11-19): lists order by a stated key ending in id; opaque cursor of the last sort key; bad cursor or limit outside 1-200 is 400 naming the parameter; services ordered by name (ignoring case and accents: the column collation) then id, with an index on (business_id, name, id). Service maxima: duration 1440, buffers 1440, price 99999999.99 (400 and DB checks). Name and description trimmed, blank description stored as null. Price always returned with two decimals.
- T8 settings (2026-11-19): maxima minNoticeMinutes 525600, cancellationWindowHours 8760, maxAdvanceDays 3650, slotStepMinutes 1440 (400 and DB checks); settings validated independently (a combination offering no slots is allowed); a settings change takes no staff lock.
- T7a details (2026-11-19): newest recovery link by created_at then greater id, and an unsent newer row already disables older links (as invites); no `PasswordChanged` when a link sets an account's first password; change-password leaves recovery links working; empty current password is 422 `CurrentPasswordIncorrect`, and the new password may equal the current one.
- Cross-cutting: `InternalError` (500) and `RequestRejected` (other HTTP-level 4xx such as 405, 413, 415; added 2026-11-17 after code review) added to the error codes; access tokens carry exactly the ADR 0010 claims; `X-Correlation-Id` header; built-in JSON console logging and DataAnnotations validation, no extra libraries, 2026-11-17.
- Outbox writer (T5): typed C# event records (`Events/`); `OutboxWriter.Add` only stages the row in the caller's DbContext, so the caller's SaveChanges and transaction decide whether it is written; correlation ID is the explicit argument, else the request's `X-Correlation-Id`, else a new ID; `eventId` = `outbox.id`, a version-7 GUID; `occurredAt` = `created_at`, written with milliseconds and `Z`; camelCase JSON, string enums, null fields kept; non-UTC times throw (R2). Payloads are checked against `specs/events/` in tests only, with Corvus.Json.Validator (Apache-2.0; JsonSchema.Net was passed over because of its maintenance-fee EULA), 2026-11-18.

Accept, resend and create-owner lock the user row (`FOR UPDATE`), 2026-11-18.
